# SyncCanvas 房间语音架构与接入方案

## 1. 文档目的

本文档描述在现有 SyncCanvas 中增加房间语音的最小可行方案，目标是让单人开发者可以较少改动地完成公网语音功能。

当前项目已经具备：

- Qt 6 客户端 `DBClient`
- GateServer HTTP 网关
- LogicServer 账号和 Token 业务
- CanvasServer/CanvasServer2 房间、画板、聊天和成员管理
- VerifyServer Node.js gRPC 服务

语音不应复用 CanvasServer 的 TCP 绘画链路。画板消息和音频媒体的传输模型不同，语音应使用专门的 WebRTC SFU。

## 2. 结论

推荐采用：

```text
LiveKit Cloud（优先）或单节点 LiveKit Server
        + LiveKit C++ Client SDK
        + VerifyServer 中的 livekit-server-sdk
        + DBClient 中独立的 VoiceManager
```

核心原则：

> CanvasServer 管画板房间，LiveKit 管语音房间，两者通过 `room_id` 和 `uid` 关联。

第一阶段不在 CanvasServer 中传输 PCM、Opus 或 RTP 数据，也不修改现有绘画同步逻辑。

## 3. 整体架构

```text
DBClient
  ├─ HTTP/JSON -> GateServer
  │                └─ VerifyServer 生成 LiveKit Token
  │
  ├─ TCP -> CanvasServer / CanvasServer2
  │         └─ 登录、房间、画板、聊天、成员、编辑权限
  │
  └─ WSS/WebRTC -> LiveKit
                    └─ 麦克风发布、远端音频订阅
```

客户端进入在线房间后的连接关系：

```text
Canvas JoinRoom 成功
    ↓
请求 /voice_token
    ↓
连接 LiveKit 房间
    ↓
发布本地麦克风
    ↓
订阅房间内其他成员的音频
```

推荐房间和用户标识映射：

| SyncCanvas 概念 | LiveKit 值 |
| --- | --- |
| 房间 `room_id=604640` | `canvas-604640` |
| 用户 `uid=1001` | `uid-1001` |
| 语音服务地址 | `wss://voice.example.com` 或 LiveKit Cloud 地址 |

## 4. 为什么不使用 CanvasServer 传语音

现有 CanvasServer 的 TCP 链路适合传输：

- 房间请求和响应
- 绘画命令
- 聊天消息
- 成员和权限广播

连续语音则需要：

- 音频采集和播放
- Opus 编解码
- jitter buffer
- 丢包恢复
- WebRTC ICE/NAT 穿透
- TURN 中继
- 多人音频转发
- 网络变化后的媒体重连

自行实现这些能力会显著扩大项目范围。LiveKit 已经提供 SFU、WebRTC 房间和客户端 SDK，因此现有 CanvasServer 可以保持稳定。

## 5. 服务端 Token 流程

### 5.1 新增接口

在 GateServer 增加：

```text
POST /voice_token
```

请求示例：

```json
{
  "uid": 1001,
  "room_id": "604640",
  "app_token": "SyncCanvas 登录 Token"
}
```

返回示例：

```json
{
  "error": 0,
  "url": "wss://voice.example.com",
  "room": "canvas-604640",
  "identity": "uid-1001",
  "token": "LiveKit JWT",
  "expires_in": 300
}
```

### 5.2 MVP 调用链

```text
DBClient
  -> GateServer /voice_token
     -> VerifyServer CreateVoiceToken
        -> livekit-server-sdk 生成 JWT
           -> 返回 url/token
```

第一阶段可以只做最基本的参数校验：

- `uid` 非空
- `room_id` 非空
- 应用登录 Token 有效

后续再补充更严格的房间成员校验。

### 5.3 LiveKit Grant

Token 至少需要包含：

```text
identity: uid-1001
room: canvas-604640
roomJoin: true
canPublish: true
canSubscribe: true
```

Token 的签名密钥只在服务端配置，客户端只接收短期访问 Token。LiveKit Token 本质上是携带参与者身份、房间和权限的 JWT。[LiveKit Token 与权限](https://docs.livekit.io/home/server/generating-tokens)

## 6. 新增依赖

### 6.1 DBClient

下载并引入 LiveKit 官方 C++ Client SDK。官方提供 Windows、Linux 和 macOS 的预编译包，也支持 CMake 集成。[LiveKit C++ SDK 快速开始](https://docs.livekit.io/transport/sdk-platforms/cpp/)

客户端 CMake 需要增加类似配置：

```cmake
find_package(LiveKit CONFIG REQUIRED)

target_link_libraries(DBClient
    PRIVATE
    LiveKit::livekit
)
```

如果使用 Qt Multimedia 负责采集和播放，还需要：

```cmake
find_package(Qt6 REQUIRED COMPONENTS Multimedia)

target_link_libraries(DBClient
    PRIVATE
    Qt6::Multimedia
)
```

不需要单独安装 WebRTC、Opus、mediasoup 或 Janus。第一阶段优先使用 LiveKit SDK 和示例中的音频接入方式。

如果所选平台没有可用的预编译 SDK，才考虑从源码构建；源码构建可能需要 Rust/Cargo 等额外工具链。[LiveKit C++ SDK 构建说明](https://docs.livekit.io/reference/client-sdk-cpp/md_docs_2building.html)

### 6.2 VerifyServer

在 `VerifyServer` 中安装 Node.js 服务端 SDK：

```bash
cd VerifyServer
npm install livekit-server-sdk
```

该 SDK 用于创建 LiveKit Access Token：[livekit-server-sdk npm](https://www.npmjs.com/package/livekit-server-sdk)

需要新增服务端配置：

```text
LIVEKIT_URL
LIVEKIT_API_KEY
LIVEKIT_API_SECRET
```

### 6.3 是否需要下载 LiveKit Server

| 部署方式 | 是否需要下载 LiveKit Server |
| --- | --- |
| LiveKit Cloud | 不需要 |
| 自己部署单节点 | 需要 Docker 镜像或官方二进制 |

建议先使用 LiveKit Cloud 验证客户端和业务流程，确认可用后再决定是否迁移到自托管。

## 7. 客户端模块设计

在 `DBClient` 中新增：

```text
VoiceManager.h
VoiceManager.cpp
```

`VoiceManager` 负责：

- 请求 `/voice_token`
- 初始化和关闭 LiveKit SDK
- 连接和断开语音房间
- 发布麦克风轨道
- 订阅远端音频轨道
- 麦克风开关
- 扬声器静音
- 语音连接状态
- 网络断开后的语音重连

`Canvas` 只负责调用 VoiceManager 和更新界面，不直接处理 LiveKit 底层对象。

建议提供以下信号：

```text
voiceConnected()
voiceDisconnected()
voiceError(QString message)
participantVoiceJoined(int uid)
participantVoiceLeft(int uid)
participantMuted(int uid, bool muted)
participantSpeaking(int uid, bool speaking)
```

第一版 UI 只需要：

- 麦克风开关按钮
- 扬声器静音按钮
- 语音连接状态提示

暂时不做单独成员音量、远程禁言和录音。

## 8. 房间生命周期

### 加入房间

```text
1. CanvasServer CanvasLogin
2. CanvasServer JoinRoom
3. DBClient 请求 /voice_token
4. VoiceManager 连接 LiveKit
5. 发布本地音频
```

### 离开房间

```text
1. VoiceManager 停止发布麦克风
2. VoiceManager 断开 LiveKit
3. CanvasServer 离开房间
4. DBClient 返回大厅
```

### 断线重连

Canvas TCP 和 LiveKit 应分别处理重连：

- CanvasServer 断开：沿用现有 `TcpMgr` 重连流程。
- LiveKit 断开：由 `VoiceManager` 单独重连或重新获取 Token。
- 网络恢复后不应假设两条连接同时恢复。

## 9. 音频采集方案

### 方案 A：Qt Multimedia

使用 `QAudioSource` 和 `QAudioSink`：

- `QAudioSource` 采集本地麦克风
- 将 PCM 数据转换成 LiveKit 音频帧
- `QAudioSink` 播放远端音频

这个方案与 Qt 客户端的设备管理结合较自然，但需要处理采样率、声道数、采样格式和线程转换。

### 方案 B：参考 LiveKit 平台音频示例

LiveKit C++ 示例集合中包含平台音频接入示例，可以先用它验证麦克风和扬声器链路，再整合到 Qt 界面。[LiveKit C++ 示例集合](https://github.com/livekit-examples/cpp-example-collection)

建议开发顺序是：

1. 先用示例或测试音频验证房间互通。
2. 再接入真实麦克风。
3. 最后处理设备切换和音频参数配置。

## 10. 部署选择

### 10.1 LiveKit Cloud

最少运维工作量：

- 不需要下载 LiveKit Server
- 不需要自己维护 TURN
- 不需要自己处理媒体 UDP 端口
- 不需要自己维护 LiveKit TLS 证书

现有后端只需要配置 LiveKit 地址、API Key 和 API Secret，并由 VerifyServer 签发 Token。

### 10.2 单节点自建

可以在现有公网服务器上新增一个 LiveKit 容器或进程：

```text
现有服务器
  ├─ GateServer
  ├─ LogicServer
  ├─ CanvasServer
  ├─ VerifyServer
  └─ LiveKit Server
```

自建时需要准备：

- LiveKit Server 镜像或二进制
- 一个可访问的域名
- WebSocket/TLS 入口
- WebRTC UDP/TCP 端口
- 必要时启用 TURN

LiveKit 官方公网部署文档列出了信令、ICE 和 TURN 端口要求。[LiveKit 端口与防火墙](https://docs.livekit.io/transport/self-hosting/ports-firewall/)

单节点自建适合学习和小规模使用；暂时不考虑多区域、自动扩容和录制集群。

## 11. 推荐实施顺序

### 阶段一：独立语音验证

- 注册 LiveKit Cloud 或启动本地 LiveKit。
- 下载 LiveKit C++ SDK。
- 在 DBClient 中创建最小 `VoiceManager`。
- 使用两个客户端加入同一个固定测试房间。
- 验证可以听到远端声音。

### 阶段二：接入 VerifyServer

- 安装 `livekit-server-sdk`。
- 增加 Token 生成函数。
- 增加 `CreateVoiceToken` gRPC 方法，或先增加临时 HTTP 接口。
- 在 GateServer 增加 `/voice_token` 路由。
- DBClient 使用真实 `room_id` 和 `uid` 获取 Token。

### 阶段三：接入 Canvas 房间

- `JoinRoom` 成功后自动连接语音。
- 离开画布时断开语音。
- 增加麦克风、扬声器和连接状态控件。
- 处理 Canvas 和 LiveKit 的独立重连。

### 阶段四：补充体验

- 成员语音状态显示。
- 麦克风设备选择。
- 扬声器设备选择。
- 单独成员音量。
- 语音错误提示和日志。

## 12. 验收标准

第一版完成后应满足：

- 两个公网客户端可以加入同一个 Canvas 房间。
- 两个客户端可以互相听到声音。
- 关闭麦克风后远端听不到本地声音。
- 离开 Canvas 房间后语音连接也会断开。
- CanvasServer 重启不会导致语音服务崩溃。
- Canvas 绘画和聊天功能不受语音连接影响。
- 客户端断网恢复后可以重新连接语音。

## 13. 暂不实现的内容

以下功能不纳入第一版：

- 自研 WebRTC 媒体服务
- CanvasServer 转发音频
- 语音录制和回放
- 远程强制禁言
- 语音消息持久化
- 多区域 SFU
- 语音房间数据同步到 MySQL
- 复杂的角色和主持人权限
